title: Extending BrainlessLab
description: Choose one narrow boundary and establish its software and evidence limits.
---

An extension should make a new question possible without changing an existing result's
meaning. Begin with a model parameter or task option when that expresses the intended
change. Add a new substrate only when its equations differ.

## Choose the smallest implementation

| Intent | Current path |
| --- | --- |
| Change a supported model | `NodeSpec.parameters` |
| Change task timing or observations | `TaskSpec.options` |
| Change node count or input scale | `CompositionSpec` |
| Compare a mechanism | Named targets and declared interventions |
| Explore parameters | Development-only `sweep` |
| Add a diagnostic | Pure offline analysis over owned result data |
| Add a new model or task family | Reviewed package implementation and resolver changes |

There is no general third-party registry or arbitrary body assembly in this release.
Historical Julia extension methods remain available at their source revision.

## Read equations and tests together

```bash
uv sync --locked --group dev
uv run pytest python/tests/test_sorn.py python/tests/test_task_validation.py
```

Use these focused suites to understand construction, update ordering, pruning, reset
and task schedule validation. A passing existing suite does not validate a new equation.

Scientific specifications remain immutable host values. Keep device buffers and memory
admission in execution. Use explicit generators and stable entity/feature IDs. Preserve
destination/source matrices and fixed ndarray ranks with runtime dimensions.

## Define the new contract before integrating it

For a model, state the old-state/new-state order, threshold equality rule, emitted
activity, readout, adaptation, frozen modes and reset. Test small hand-calculated states
with an independent NumPy reference. Include non-finite drives, empty connectivity,
inactive slots, owned snapshots and batch independence.

For a task, state available observations, action cadence, response windows, ties,
termination, native units and scoring opportunity. Validate initial schedules before
device allocation. Keep labels and hidden task truth outside the online controller.
Choose an appropriate reference policy without calling its observed score an upper bound.

For offline analysis, preserve the independent unit and prevent fit/validation leakage.
For a backend change, qualify the arithmetic/device path separately from model equations.

Only after those checks should you profile runtime costs or propose an optimisation.
Preserve a single equation source when introducing fused execution. Canonical ndarray
access and explicit returned status values avoid stale reads across aliased helper views.
