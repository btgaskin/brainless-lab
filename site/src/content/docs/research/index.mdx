---
title: Research records
description: How BrainlessLab retains exact run configurations now, and how a searchable record catalogue can grow next.
---

The research area is a small index over standard BrainlessLab records. It does not add a
database or a new execution path.

## Current contract

Every repeated run uses an operation plan and writes one portable record:

```text
record-id/
├── record.toml
├── request.toml
├── resolved.toml
├── seeds.csv
├── data/
├── summary/
├── figures/
├── report/index.html
└── DONE
```

`request.toml` retains the exact submitted configuration. `resolved.toml` retains defaults
and derived values. The seed ledger, raw tables, summary, Git revision, Julia version,
checksums, and completion state make the run reviewable and shareable.

An `ExperimentSpec` groups operation plans under one question and version. Each operation
still writes its own standard record. A benchmark is one operation type, not the parent of
all research.

## Current public indexes

- [Benchmarks](/benchmarks/) lists versioned benchmark protocols and records.
- [Experiments](/experiments/) lists versioned questions and their evidence states.
- [Experimental](/experimental/) lists software capabilities, not research results.

This phase includes one real benchmark record and one planned experiment. The pages prove
the catalogue structure without pretending that a complete research archive exists.

## Next catalogue phase

A later build can discover completed records and derive catalogue rows directly from their
files. Each row should expose:

- stable research ID and protocol version;
- operation type and completion state;
- evidence state and seed stage;
- node, task, body, condition, and user-defined tags;
- creation time, Git revision, package version, and Julia version;
- request, resolved configuration, summary, report, and record paths.

The interface can then search free text, filter tags and evidence state, and sort by time,
operation, task, node, or version.

Keep records immutable after publication. Add annotations or a superseding protocol rather
than rewriting old output. Derive measured values from the machine-readable summary instead
of copying them into page frontmatter.

## What remains open

The next phase must decide which record roots are indexed, how large data files are
archived, and how private or sealed records are excluded. It must also define stable
user-supplied tags without turning registry membership into an acceptance gate.

Until then, use a deliberate records root and retain the full standard bundle for every
repeated run.
